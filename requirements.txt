# PART 7 — Workflow A: Run Tests

Your first GitHub Actions workflow should run **only for pull requests targeting `main`**.

Check it:

```bash
cat .github/workflows/tests.yml
```

It should have something conceptually like:

```yaml
name: Run Tests

on:
  pull_request:
    branches:
      - main

jobs:
  test:
    runs-on: ubuntu-latest

    steps:
      - uses: actions/checkout@v4

      - name: Set up Python
        uses: actions/setup-python@v5
        with:
          python-version: "3.12"

      - name: Install dependencies
        run: pip install -r requirements.txt

      - name: Run tests
        run: python -m pytest
```

### Why `pull_request`?

Because the exercise wants GitHub to check code **before it enters `main`**.

If you only used:

```yaml
on: push
```

the code could already be pushed to `main` before CI complained.

# PART 8 — Workflow B: Coverage

Check:

```bash
cat .github/workflows/coverage.yml
```

You need:

```yaml
name: Enforce Coverage

on:
  pull_request:
    branches:
      - main

jobs:
  coverage:
    runs-on: ubuntu-latest

    steps:
      - uses: actions/checkout@v4

      - name: Set up Python
        uses: actions/setup-python@v5
        with:
          python-version: "3.12"

      - name: Install dependencies
        run: pip install -r requirements.txt

      - name: Run tests with coverage
        run: python -m pytest --cov=src --cov-report=term-missing --cov-fail-under=85
```

The critical part is:

```bash
--cov-fail-under=85
```

### What it does

If coverage is:

```text
87%
```

→ command succeeds.

If coverage is:

```text
73%
```

→ command fails.

That is what turns coverage from a **number being displayed** into a **CI requirement**.
